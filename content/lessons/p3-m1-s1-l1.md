# Modelar el dominio en once tablas

Un backend no empieza por los endpoints: empieza por decidir qué cosas existen y cómo se relacionan. CropEye lo resolvió con once tablas en PostgreSQL 16 y una API FastAPI que expone esas entidades. El número no es arbitrario; once tablas alcanzan para separar identidad, catálogo, operación y trazabilidad sin caer en un modelo inflado.

## Cuatro preocupaciones, once tablas

El esquema se puede leer por dominios, aunque las tablas exactas vivan en el repositorio `cropeye-backend`:

- **Identidad:** usuarios, credenciales y tokens de refresco. Es la base del control de acceso.
- **Catálogo:** cultivos y clases de enfermedad que el sistema reconoce. Conecta la taxonomía agronómica con la salida del modelo.
- **Operación:** análisis, imágenes asociadas y resultados. Es el corazón del producto.
- **Trazabilidad:** estados, eventos y registro de auditoría. Permite reconstruir qué pasó y quién lo hizo.

Separar estas cuatro preocupaciones tiene un efecto práctico: un cambio en el catálogo no debería tocar la autenticación, y un cambio en el almacenamiento de imágenes no debería reescribir el historial. Cuando esa separación se respeta, las migraciones son más pequeñas y los errores más localizables.

## Errores con forma estable

FastAPI facilita devolver JSON, pero cada equipo inventa su propio formato de error si nadie lo impide. CropEye adoptó RFC 7807, el estándar de «problemas» para HTTP, con el tipo de contenido `application/problem+json`. Todos los errores comparten los mismos campos: un tipo, un título, el código de estado, un detalle legible y la instancia donde ocurrió.

```json
{
  "type": "about:blank",
  "title": "Solicitud inválida",
  "status": 422,
  "detail": "El cultivo indicado no es válido.",
  "instance": "/analisis"
}
```

La ventaja no está en la elegancia, sino en la predictibilidad: la app puede mostrar `detail` sin inspeccionar cada endpoint, y los logs se pueden agrupar por `type`. Un contrato de error estable es tan importante como el contrato de éxito.

## El tamaño de la suite

El backend acumula alrededor de 200 funciones de prueba sobre 10.212 líneas de código. Es una proporción sana para un proyecto de tesis: hay más código que pruebas, pero las pruebas cubren los caminos principales de identidad, análisis y estados.

Hay un detalle que cambia la lectura del número: las pruebas corren sobre SQLite, mientras que las que requieren PostgreSQL quedan omitidas. SQLite no reproduce todos los comportamientos del motor real —tipos, restricciones, concurrencia, funciones específicas—, así que una suite verde no garantiza que el sistema funcione igual en producción.

:::warning
Una prueba omitida no es una prueba aprobada. Si el entorno de integración continua no levanta PostgreSQL, las partes del backend que dependen del motor real quedan sin verificación efectiva.
:::

## La tensión del esquema

Once tablas son suficientes para el alcance actual, pero también fijan decisiones. Guardar el resultado del modelo como un conjunto de columnas hace fácil consultar por clase y difícil incorporar un modelo con otra taxonomía. Normalizar en exceso mejora la consistencia y encarece cada lectura. El esquema de CropEye eligió un punto medio: suficiente estructura para auditar, suficiente flexibilidad para iterar.
