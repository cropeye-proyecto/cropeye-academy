# Quién puede hacer qué

Un sistema que guarda diagnósticos agrícolas necesita saber quién consulta qué. CropEye resuelve la identidad con JWT de acceso y refresco, dos roles explícitos y un bloqueo temporal tras cinco intentos fallidos. Cada una de esas piezas responde a una amenaza concreta, y cada una introduce un costo que conviene entender.

## El ciclo del token

El acceso se hace con un par de tokens. El token de acceso es de vida corta y viaja en cada petición; el de refresco permite obtener uno nuevo sin volver a pedir la contraseña. La separación reduce la ventana de daño si un token de acceso se filtra.

```text
1. login            → access_token (corto) + refresh_token (largo)
2. petición normal  → Authorization: Bearer <access_token>
3. access vencido   → POST de refresco con refresh_token
4. refresco válido  → nuevo access_token
5. refresco revocado o vencido → volver a iniciar sesión
```

Ninguna implementación seria guarda la contraseña en claro: se almacena un hash. El refresh token, en cambio, necesita poder revocarse; para eso el servidor debe llevar algún registro de los tokens emitidos. Esa diferencia explica por qué cerrar sesión en un dispositivo puede invalidar el refresco sin afectar a los demás.

## Dos roles, una frontera

El control de acceso basado en roles distingue USUARIO y ADMINISTRADOR. Un usuario puede crear análisis y consultar los propios; un administrador puede ver el conjunto, gestionar catálogos y revisar la auditoría. La RFC-04 tomó una decisión importante: las funciones administrativas se exponen únicamente a través de la API bajo `/admin`, no desde la aplicación móvil.

Esa restricción reduce la superficie de ataque y también el alcance de la app: la aplicación no necesita pantallas de administración ni lógica de permisos compleja. La contrapartida es que el equipo debe operar el panel por otra vía, con las herramientas de API.

## El bloqueo tras cinco intentos

Tras cinco intentos fallidos, la cuenta se bloquea temporalmente. El objetivo es frenar la fuerza bruta contra contraseñas débiles, que es el ataque más común contra un login. El costo es que un atacante que conozca un nombre de usuario puede provocar el bloqueo y negar el servicio a esa persona. Por eso el bloqueo debe ser temporal y no permanente, y debe registrarse en la auditoría.

:::warning
El archivo `.env.example` del backend incluye un secreto JWT por defecto y una contraseña de base de datos de ejemplo. Un valor por defecto que llega a producción invalida todo el esquema: cualquiera que lea el repositorio puede firmar tokens válidos. Estos valores deben rotarse y nunca versionarse.
:::

## La tensión entre seguridad y fricción

Cada control agrega fricción. Tokens cortos obligan a refrescar; el bloqueo obliga a esperar; los roles obligan a decidir permisos antes de escribir el endpoint. La tentación es relajar todo para la demo, y es exactamente lo que produce sistemas que funcionan en la presentación y fallan en el primer uso real.

La auditoría es la pieza que cierra el círculo: no impide una acción, pero deja registro de quién la hizo y cuándo. En un sistema con datos agronómicos, ese registro vale tanto como el control de acceso.
