# El atajo que rompe la arquitectura

La aplicación de CropEye no habla con el backend. Habla directamente con la API de inferencia en `10.0.2.2:8000`. El backend existe, tiene once tablas, autenticación y auditoría, y escucha en el puerto 8100 sin recibir las peticiones de la app. Esa diferencia entre el diseño y el código es la deuda más importante del proyecto.

## Qué hace el atajo

```text
diseñado:   app → backend :8100 → API de IA :8000
implementado: app →────────────────→ API de IA :8000
```

La app captura la foto, la comprime y la envía. Recibe clase, confianza y Grad-CAM. Funciona. Para una demostración, el atajo elimina la necesidad de levantar PostgreSQL, migrar el esquema y configurar usuarios. La pregunta es qué se pierde cuando el atajo se convierte en la única vía.

## Las cuatro pérdidas

**Identidad.** La API de inferencia no pide credenciales. Cualquiera que alcance el puerto puede clasificar imágenes, consumir cómputo y agotar la capacidad del servicio.

**Persistencia.** Ningún análisis se guarda en las once tablas. El historial vive solo en el teléfono y desaparece al desinstalar la app.

**Auditoría.** No queda registro de quién consultó qué ni cuándo. La tabla de auditoría del backend nunca se llena en el flujo real.

**Estados.** El ciclo PENDIENTE, PROCESSING, COMPLETADO, RECHAZADO y ERROR no se ejecuta. Cada análisis es una petición síncrona sin rastro.

```text
con backend:   auth → validación → registro PENDIENTE → inferencia → estado final → auditoría
sin backend:   inferencia → respuesta → historial local
```

## Por qué ocurrió

Un atajo así no nace de una decisión arquitectónica deliberada, sino de una suma de urgencias. La API de inferencia ya estaba lista y respondía; el backend requería base de datos, migraciones y configuración. Conectar la app al servicio que ya funcionaba permitió avanzar en la demo y dejar la integración para después. El «después» nunca llegó.

Es un patrón común en proyectos académicos y también en productos reales: la pieza más fácil de probar se convierte en la ruta principal, y la pieza que aporta gobierno queda como deuda.

:::warning
Un backend que no recibe tráfico no se valida. Sus pruebas pueden pasar, pero nadie descubre los problemas de integración hasta que se conecta de verdad. Cuanto más tiempo pasa, más caro es el cambio.
:::

## Cómo se corrige

La corrección no requiere reescribir la app: requiere cambiar su URL base, agregar autenticación y ajustar el contrato. El backend ya tiene el adaptador de inferencia, el ciclo de estados y la persistencia. La app necesitaría login, un endpoint de creación de análisis y una consulta de estado.

El costo real está en el medio: sesiones, manejo de errores, reintentos y migración del historial local a un historial con dueño. Es trabajo de integración, no de modelo, y por eso suele postergarse.

## La lección

Una arquitectura no se valida por lo que el diagrama promete, sino por el camino que recorren las peticiones. Si la ruta principal evita el backend, el backend es documentación ejecutable, no sistema.
