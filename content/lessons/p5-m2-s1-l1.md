# El costo de mantener dos backends

En la organización `cropeye-proyecto` conviven cuatro repositorios. Tres forman el sistema actual; el cuarto, `cropeye-api`, es un backend anterior que fue reemplazado por `cropeye-backend` y nunca se archivó. Un repositorio obsoleto no ejecuta nada, pero sigue costando.

## El inventario

```text
cropeye-app       Flutter            en uso
cropeye-ia        modelo + API       en uso
cropeye-backend   FastAPI + Postgres en uso
cropeye-api       backend anterior   obsoleto, sin archivar
```

`cropeye-api` cumplió una función: fue el primer intento de backend del proyecto. Cuando el equipo decidió reescribir sobre FastAPI y PostgreSQL 16, el repositorio quedó atrás. El reemplazo quedó registrado en la historia del proyecto, pero el código viejo permanece accesible con el mismo nivel de visibilidad que el nuevo.

## Los costos concretos

**Confusión en el onboarding.** Alguien que llega al proyecto ve dos backends y no sabe cuál es el vigente. La documentación ayuda solo si está actualizada, y en este proyecto no siempre lo está.

**Esquemas divergentes.** Dos backends implican dos modelos de datos. Cualquier cambio en el dominio —una tabla nueva, un campo nuevo— debe decidir si se replica en el obsoleto o se ignora. Ignorarlo es correcto y aun así genera dudas.

**Superficie de seguridad.** Un repositorio con credenciales de ejemplo, dependencias viejas y sin mantenimiento sigue siendo código que alguien puede desplegar por error. La deuda de seguridad no se mide por uso, sino por posibilidad.

**Ruido en las métricas.** Las métricas de la organización —commits, issues, actividad— mezclan dos proyectos. Un backend abandonado sigue contando como parte del sistema.

:::note
Archivar un repositorio en GitHub lo deja de solo lectura y conserva el historial. Es la forma más limpia de decir «esto existió y ya no se mantiene» sin borrar evidencia. Borrarlo elimina contexto; dejarlo activo invita a equivocarse.
:::

## La tensión entre historia y claridad

Hay una razón legítima para conservar `cropeye-api`: documenta el camino recorrido y permite entender por qué se migró. La historia técnica tiene valor, sobre todo en un proyecto de tesis donde las decisiones cuentan tanto como el resultado.

Esa razón no exige que el repositorio parezca vigente. Un `README` que diga «obsoleto, ver cropeye-backend» y un repositorio archivado resuelven el problema sin perder nada. Lo que no se justifica es la ambigüedad.

## Qué enseña este caso

Los proyectos no solo acumulan código: acumulan versiones de sí mismos. La disciplina de retirar lo que ya no se usa es tan importante como la de escribir lo nuevo. Un repositorio obsoleto sin marcar es una trampa para la próxima persona, que casi siempre es uno mismo seis meses después.

> **Para llevarte:** el mismo patrón —prometer más de lo que se ejecuta— aparece en el despliegue. La última lección de esta ruta contrasta la infraestructura documentada con la que realmente corre.
