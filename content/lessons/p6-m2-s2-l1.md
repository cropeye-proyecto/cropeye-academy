# Checklist de auditoría técnica

Auditar un proyecto no es buscar culpables: es comparar lo que el sistema dice ser con lo que realmente hace. CropEye es un caso rico porque tiene documentación abundante, código real y varias distancias entre ambos. Esta lección convierte esas distancias en una checklist.

## La checklist

```text
[ ] ¿El repositorio clonado se ejecuta sin pasos no documentados?
[ ] ¿Existe una imagen o un entorno reproducible por servicio?
[ ] ¿El pipeline ejecuta las pruebas en cada cambio?
[ ] ¿Las pruebas corren contra el mismo motor que producción?
[ ] ¿Los secretos de ejemplo son distintos de los de producción?
[ ] ¿La configuración de CORS es coherente con el uso de credenciales?
[ ] ¿Los artefactos del modelo están versionados o accesibles?
[ ] ¿El número de clases coincide entre informe, modelo y base de datos?
[ ] ¿El formato del artefacto coincide con el que carga el código?
[ ] ¿El recorrido real de las peticiones coincide con el diagrama?
[ ] ¿Hay repositorios obsoletos sin archivar?
[ ] ¿Quedan marcadores [COMPLETAR] en la entrega final?
```

## Lo que encuentra en CropEye

Cada casilla tiene una respuesta concreta. El clon no predice porque `models/` está ignorado y los pesos no viajan con el código. No hay Dockerfile ni CI en ninguno de los cuatro repositorios, y el único servicio orquestado es PostgreSQL. Las pruebas corren sobre SQLite mientras las de PostgreSQL se omiten. El `.env.example` incluye un secreto JWT y una contraseña por defecto. CORS usa `allow_origins=["*"]` junto con `allow_credentials=True`, una combinación que los navegadores rechazan y que en cualquier caso no es una política.

El modelo v4 documenta trece clases más «Otra», la RFC-05 fija nueve y el Informe 3 declara trece. La RFC-03 promete ONNX y el código ejecuta PyTorch. La app llama directo a la API de inferencia. `cropeye-api` sigue activo. El Informe 3 conserva `[COMPLETAR]`.

```text
deuda                                   severidad
app evita el backend                    alta (seguridad + trazabilidad)
secretos por defecto                    alta
pesos del modelo ausentes del clon      alta (reproducibilidad)
sin CI ni Dockerfile                    media-alta
pruebas solo en SQLite                  media
CORS permisivo con credenciales         media
documentación desincronizada            media
repositorio obsoleto sin archivar       baja-media
```

## Cómo usar la checklist sin convertirla en linchamiento

Una auditoría sirve si produce un plan. Los hallazgos se priorizan por dos ejes: impacto y esfuerzo. Cambiar la URL base de la app y exigir autenticación es barato y de alto impacto. Reescribir el esquema de clases es caro y requiere datos nuevos. Publicar los pesos y agregar un Dockerfile es barato y desbloquea la reproducibilidad.

:::note
Una deuda documentada vale más que una deuda oculta. El problema de CropEye no es tener brechas —casi todo proyecto las tiene—, sino que los informes las presenten como si no existieran.
:::

## La tensión del cierre

Cerrar un proyecto académico empuja a mostrar lo mejor y esconder lo incompleto. La tentación es escribir «implementado» donde corresponde «prototipado» y confiar en que nadie mirará el repositorio. La auditoría propone lo contrario: declarar el estado real con la misma precisión que los aciertos.

Un sistema honesto sobre sus límites es más fácil de mejorar y más creíble. El 0,908 de F1 en campo vale porque se midió contra 801 fotos que el modelo nunca vio; el resto del proyecto merece la misma disciplina.

> **Para llevarte:** con esta checklist cierras el recorrido. Vuelve a la ruta que más te haya costado y léela con la mirada del auditor: cada número y cada afirmación deberían poder verificarse en el repositorio.
